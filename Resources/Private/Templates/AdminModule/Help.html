Passkey Management Help

This guide explains how to roll out passkeys to your backend users, handle recovery scenarios, and understand how passkeys interact with TYPO3's multi-factor authentication (MFA).

Rolling out passkeys

A phased rollout lets you introduce passkeys gradually, giving users time to register their devices before enforcement becomes mandatory.

Step 1 — Install the extension

Install netresearch/nr-passkeys-be via Composer and activate it in the Extension Manager. No database schema changes are required beyond the automatic table creation for tx_nrpasskeysbe_credential.

Step 2 — Configure extension settings

In Admin Tools > Settings > Extension Configuration, review the settings for nr_passkeys_be. Key options include the Relying Party name (displayed during WebAuthn ceremonies) and whether discoverable (usernameless) login is enabled.

Step 3 — Set groups to Encourage

On the Dashboard tab, change a group's enforcement level to Encourage. Users in that group will see a non-blocking banner on every backend login reminding them to register a passkey. They can dismiss the banner and continue working normally.

Start with a pilot group (e.g., your admin team) to validate the workflow before widening the rollout.

Step 4 — Set groups to Required

When you are confident the process works, change the group to Required. Users who have not yet registered a passkey will see a full-screen interstitial after password login. The interstitial guides them through passkey registration and shows how many grace-period days remain.

During the grace period users can skip the interstitial and continue to the backend, but they will see it on every login until they register a passkey or the grace period expires.

Step 5 — After the grace period expires

Once the grace period ends, enforcement becomes strict: users must register a passkey before they can access the backend. The interstitial can no longer be skipped.

Step 6 — Monitor adoption

Use the Dashboard tab to track overall adoption rates, per-group progress, and identify users who have not yet registered passkeys.

Recovery procedures

When a user loses access to their authenticator device (phone lost, security key broken, laptop replaced), follow these steps:

1. User reports lost device

The user contacts an administrator and reports which device or authenticator is no longer available.

2. Admin revokes affected passkey(s)

Open the user's be_users record in System > Backend Users. In the Passkeys section, locate the affected credential(s) and delete them. If the device name is not clear, the user can identify the credential by its registration date or the authenticator type.

3. User has zero passkeys and group enforcement is active

If the user's group is set to Required or Enforced and the user now has zero registered passkeys, the next password-based login will trigger the mandatory setup interstitial. The user is guided through registering a new passkey on their replacement device before they can continue.

4. User cannot log in at all

If the user has no working authenticator and cannot complete the password-based login flow (e.g., the only registered passkey was their sole credential), the administrator can:

  • Temporarily lower group enforcement — switch the group from Enforced/Required to Encourage or Off so the user can log in with a password.
  • Reset the user's password — if the password has also been forgotten, reset it in the be_users record so the user can log in and re-register a passkey.
Remember to restore the group's enforcement level after the user has re-registered a passkey. Leaving enforcement lowered indefinitely weakens your security posture.

Passkeys & MFA (two-factor authentication)

A passkey combines something you have (the device or security key) with something you are (biometric) or something you know (device PIN). It is also phishing-resistant by design — cryptographically bound to the origin and cannot be replayed elsewhere. For most TYPO3 backends, passkey-only login is stronger than password + TOTP.

The TYPO3 MFA policy is all-or-nothing — by default

TYPO3's built-in MFA requirement ($GLOBALS['TYPO3_CONF_VARS']['BE']['requireMfa']) applies regardless of how the user authenticated. That creates an operational dilemma for teams that want passkeys instead of TOTP:

TYPO3 MFA policy Passkey user Password user
Required (on) MFA prompt blocks passkey-only login — user must also complete TOTP MFA enforced — standard TYPO3 behaviour
Off Passkey-only login works Password-only login becomes possible — no second factor at all

The highlighted row is the password-only loophole: if you disable TYPO3's MFA requirement to let passkey users in with just one step, users without a passkey can suddenly log in with only a password. This is a security regression.

Closing the loophole

This extension provides two settings that let you enforce "passkey = MFA satisfied, password = still requires MFA" and prevent the regression:

  • skipMfaOnPasskeyAuth (default: enabled) — after a successful passkey login, the TYPO3 MFA challenge is skipped for that session. The passkey has already proven multi-factor. Password logins still go through MFA normally.
  • disablePasswordLogin (default: disabled) — blocks password-based login for users who have a registered passkey, preventing fallback.

Recommended production combination

For the strongest security posture with the least friction:

  1. Keep TYPO3's requireMfa policy enabled (protects password users).
  2. Keep skipMfaOnPasskeyAuth enabled (passkey users skip the redundant TOTP prompt).
  3. Roll out per-group passkey enforcement up to Required (users in critical groups must register a passkey).
  4. Enable disablePasswordLogin once adoption is high enough (closes the password fallback entirely).

When to keep MFA on top of passkeys

Disable skipMfaOnPasskeyAuth only if:

  • Your security policy explicitly mandates defence-in-depth with independent factors regardless of the primary factor's strength.
  • You need compliance with a standard that prescribes a separate MFA step (e.g. PCI-DSS in specific configurations).
  • Your threat model seriously considers authenticator device compromise.

Login pipeline order

With skipMfaOnPasskeyAuth enabled, the backend login pipeline processes requests as follows:

  1. Authentication — passkey (priority 80) or, if no passkey payload is present, password.
  2. MFA challenge — skipped for passkey logins; prompted for password logins if a provider is configured and the TYPO3 policy requires it.
  3. Passkey interstitial — only for password-authenticated users whose group requires a passkey.
  4. Backend rendering — normal access.
